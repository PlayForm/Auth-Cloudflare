# Cloudflare plugin - Release workflow

> [!IMPORTANT]
>
> Tag format is `Cloudflare/v<semver>` (e.g. `Cloudflare/v0.0.1`) - the
> `Build.yml` workflow triggers on `Cloudflare/v*` and attaches per-target
> `auth-cloudflare-<target>.tar.gz` + `auth-hermes-cloudflare-<target>.tar.gz`
> assets plus a per-target `SHA256SUMS-<target>.txt` checksum file. Never use
> a bare `v*` tag.

## Release checklist

1. **Version sync** - one version across:
    - `crates/auth-cloudflare/Cargo.toml`
    - `crates/auth-hermes-cloudflare/Cargo.toml`
    - `package.json`
    - `plugins/auth-hermes-cloudflare/plugin.yaml`
2. **BINARY_VERSION** - update `plugins/auth-hermes-cloudflare/BINARY_VERSION` with the
   plain version (`0.1.0`, no `v`, no tag prefix). `download.sh` reads this
   first; the GitHub-API fallback parses `Cloudflare/v<tag>`.
3. **Changelog** - add a `CHANGELOG.md` entry for the version.
4. **Push the child submodule BEFORE tagging.** A release commit that bumps
   the parent gitlink to a NEW child commit must have that child commit on
   the child's remote already: the tag-triggered Build/Publish checkouts
   fail with `fatal: remote error: upload-pack: not our ref <child-sha>`
   when the child remote lacks it (the runner checks out the submodule at
   the gitlink). `git -C plugins/auth-hermes-cloudflare push Source Current`
   first, then tag the parent.
5. **Tag + push**:
    ```sh
    git tag Cloudflare/v0.0.1
    git push Source Cloudflare/v0.0.1
    ```
6. **Verify** - the workflow uploads one artifact per target; check the
   release page lists `aarch64-apple-darwin`, `x86_64-apple-darwin`,
   `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`.

## If Finalize's child push fails (PLAYFORM_RELEASE_PAT)

The Finalize job commits `SHA256SUMS.txt` inside the runner's child clone
BEFORE pushing; a revoked/expired `PLAYFORM_RELEASE_PAT` then fails the push
(`remote: Invalid username or token`) and Build goes red, so Publish's
gitlink job never advances the gitlink. The release assets and the GitHub
release already exist and the Publish workflow's Test + crate-publish jobs
run independently of Build - crates still publish. Replicate Finalize
manually:

1. Rebuild the in-tree `plugins/auth-hermes-cloudflare/SHA256SUMS.txt`
   from the release's four per-target `SHA256SUMS-<t>.txt` assets - exact
   format: `BINARY_VERSION: <v>` header, blank, `# GENERATED BY Build.yml -
   do not edit by hand.`, blank, then per-target blocks with each checksum
   line indented 2 spaces and a blank line after each block.
2. Commit it in the child on `Current` (message `chore: update in-tree
   SHA256SUMS.txt for v<v> (Build.yml)`), push the child.
3. Float the parent gitlink to the new child tip and push the parent. The
   Bump-Plugin-Gitlink job then finds "nothing to bump" (benign).
4. Verify the three-way consistency: child `BINARY_VERSION` file == in-tree
   `SHA256SUMS.txt` header == the release tag version - a strict
   `download.sh` REFUSES on mismatch.

### Re-running Finalize after the manual replication (and the gitlink job)

When the gitlink tree ALREADY carries a previous version's `SHA256SUMS.txt`
(every release after the first), Finalize's re-run fails differently: it
regenerates the sums at the tag's gitlink (a local modification) and then
`git checkout Current` refuses (`Your local changes to the following files
would be overwritten by checkout: SHA256SUMS.txt`) because Current has moved
ahead. Fix: REWIND the child to the gitlink TREE via an append-only revert
(`git revert <sums-commit>` restores the old sums file - never force-push /
reset), push the child, then re-run Finalize: its checkout no-ops (identical
trees) and it re-commits the fresh sums with the (now valid) PAT.
After that, the Publish `Bump-Plugin-Gitlink` job can still stay red
permanently: it commits its gitlink bump on the TAG base and pushes Current,
which has moved ahead of the tag (auto-committer, manual floats), so the
push is always non-fast-forward. That failure is cosmetic - the job's
objective (gitlink == child tip) is already met by the manual float; verify
`git submodule status` shows no `+` and do not chase a green rerun.

## Version bumps

- Rust API/behavior change → bump minor, keep the plugin shim in lockstep.
- Plugin-only fix (no crate change) → bump `plugin.yaml` version only; the
  crates may trail.
- The executable's JSON CLI protocol is not stable across versions - `download.sh` always fetches the
  exact `BINARY_VERSION`, never "latest" for an existing install.

### Every version bump touches these files

`crates/auth-cloudflare/Cargo.toml`, `crates/auth-hermes-cloudflare/Cargo.toml`
(both the package version AND the `auth-cloudflare` path-dep pin),
`package.json`, `README.md` badges (release + plugin),
`plugins/auth-hermes-cloudflare/{plugin.yaml,BINARY_VERSION,README.md}`,
`plugins/auth-hermes-cloudflare/fixtures/auth_cloudflare_version.json`, and
`docs/catalog.generated.*` (re-export, which stamps `Plugin: <version>`).

### Local verification order (the plugin tests gate on the binary version)

`plugins/auth-hermes-cloudflare/tests/test_real_binary.py` compares the
INSTALLED binary against `BINARY_VERSION`, so after bumping it four tests fail
with `package_version 0.0.x is older than the required 0.0.y` until the new
binary is installed:

```sh
cargo install --path crates/auth-cloudflare --force
target/release/auth-hermes-cloudflare link --source <cargo bin>/auth-cloudflare
```

Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D
warnings`, `cargo test --workspace`, then the plugin pytest suite with
`HERMES_AGENT_SRC` and the hermes venv's site-packages on `PYTHONPATH`.

### Regenerate docs from the LIVE cache, not from the fixtures

`Check.yml`'s docs job seeds a scratch cache from
`crates/auth-cloudflare/fixtures/models/*.json` (7-8 records) and only asserts
the export works - it never compares against the committed docs. Regenerating
`docs/catalog.generated.*` the same way SHRINKS the committed docs to the
fixture subset. Export against the refreshed live cache instead:

```sh
auth-cloudflare catalog refresh                       # needs CLOUDFLARE_API_TOKEN
AUTH_CLOUDFLARE_EXPORT_DIR="$PWD/docs" auth-cloudflare catalog export yaml
AUTH_CLOUDFLARE_EXPORT_DIR="$PWD/docs" auth-cloudflare catalog export markdown
```

## ureq must stay 2.x

`ureq` 3.x renamed the `tls` feature (and reshaped `Error::Status`), so a
dependabot `ureq` 3.x bump fails EVERY check (cargo test, clippy, fixtures)
with `package depends on ureq with feature 'tls' but ureq does not have that
feature`. The workspace pin `ureq = { version = "2.12", ... }` is load-bearing
- revert any 3.x bump to 2.12 and commit (never reset); the auto-merge bot
re-applies the bump periodically, so consider a dependabot ignore rule.
Also: when the development default model changes, update the hardcoded
default-model-id grep in `Check.yml`'s offline fixtures-docs job - it greps
the regenerated `catalog.generated.yaml` for the current default id.
